# Real run on a scratch repository, 2026-10-25

This is the first run in which the workflow produced real code, ran real tests, and was reviewed from the actual diff, instead of describing what it would do. It is a small run and a weak test; read the limits first.

Setup: a fictional 25-line cart library (Cartlite, Node, integer cents) with a seeded defect: a fixed coupon larger than the cart makes the total negative. The work followed `fix-or-build-to-merge` on the light path with a Low risk recorded. Builder and reviewers were Claude subagents of the same model family. The workflow requires distinct families, so a real run would have stopped before review; the independence rule was waived here on purpose, to test the mechanics. Diffs: [correct fix](2026-10-25-real-run/fix-correct.diff) and [flawed fix](2026-10-25-real-run/fix-flawed.diff).

## Part 1: a correct fix

The builder reproduced the defect with two new tests that failed before the one-line fix and passed after it, ran the full suite, and wrote a regression review. A first reviewer (independent review, light path) returned PASS with two Minor out-of-scope findings (a percent coupon over 100 and a negative fixed value still misbehave). An adversarial reviewer, added for comparison, also returned PASS and raised the same percent-over-100 point as a question for the owner.

## Part 2: a seeded flaw

A second fix clamped the total only when exactly one coupon was applied, with a test for one coupon only. The independent reviewer and the adversarial reviewer each returned FAIL with a Moderate finding, reproduced with two coupons (-700), plus a finding that the test could not catch it.

## What this shows

- On these two revisions the light path (one reviewer) reached the same verdicts as the standard path (two). It did not miss the seeded flaw. One flaw, one run, one model family is not enough to say the light path is as safe.
- The adversarial review added no finding the independent review lacked on the flawed revision. It gave extra attack evidence on the correct fix.

## What it found in the workflow

- Stage 2 worked: the builder reported that `main` did not exist, Node 20 was not installed, and `npm test` failed on Node 22 (a fault in the fixture's test script, not the workflow). It then proceeded with a substitute test command and a self-created branch. The workflow did not say what to do. Fixed in 0.6.1: state the substitute and get it confirmed.
- The workflow did not say who runs the regression review; the builder ran it on its own change. Fixed in 0.6.1: it is the builder's own check and reviewers verify its coverage claims.
- Reviewers saved only a stub of their reports because the run told them not to write files. That was the run's setup, not the workflow.

## Limits

Same model family for builder and reviewers (the reviewers named themselves as the same model), one seeded defect, a trivial codebase, author-written fixtures, and author-judged results. It shows the stages can be followed with real code, and the light path can catch a plain logic gap. It does not show that it catches subtle defects or that the saving in cost is worth any lost coverage.
