# Discovery to Definition: cheese shop app (fictional case)

## Stage 1: Define requirements

**Requirements: Cheese shop app.** The only source is the one-sentence brief.

| ID | Requirement | Priority | Source | How verified |
|---|---|---|---|---|
| R1 | A visitor can see the list of cheeses available today. | Unspecified | Brief: "show today's cheeses" | Inspection: the list shown matches the shop's list for today |
| R2 | The list shows only cheeses marked available for the current date. | Unspecified | Brief: "today's" (inferred) | Test: a cheese marked unavailable does not appear |
| R3 | A visitor can submit a reservation. | Unspecified | Brief: "take reservations" | Test: a submitted reservation reaches the shop |
| R4 | The visitor gets a confirmation that the reservation was received, or a clear failure message. | Unspecified | Inferred (gap: the brief says nothing about error handling) | Test: submit a valid reservation, then a failing one |

The brief states no priorities. Q5 asks the owner to set them.

**Constraints:** none stated. "Simple" is a preference and does not bind anything. No platform is named.

**Assumptions**

| ID | Assumption | Consequence if wrong | Who can confirm |
|---|---|---|---|
| A1 | Shop staff can update "today's cheeses" each day. | R1 and R2 can't be met, so a content process is needed | Shop owner |
| A2 | Visitors don't need an account to view the list. | The flow would need a sign-in step | Shop owner |

**Open questions**

| ID | Question | Decision it blocks | Owner |
|---|---|---|---|
| Q1 | What is being reserved: cheese held for pickup, a table, or a tasting? | The reservation flow (R3, R4), its fields, and how capacity works | Shop owner |
| Q2 | Who uses the app: customers, staff, or both? | Scope of the staff-side update function (A1) | Shop owner |
| Q3 | What platform is it for (web, mobile)? | Navigation conventions in stage 4 | Shop owner |
| Q4 | What accessibility target applies? | Verification criteria | Shop owner |
| Q5 | How should R1–R4 be ranked? | Scope and build order | Shop owner |

**Non-goals:** none stated. Payment, inventory management, and online ordering are not mentioned and are not assumed in scope.

## Stage 2: Ground users and survey solutions

**Personas: skipped.** There is no user research. The workflow says to carry forward an assumptions-and-research-needs list instead:

- Assumed: customers check the list before they visit. To confirm, interview a few customers, or ask the owner how customers ask about stock today.
- Assumed: customers mostly use phones. To confirm, ask the owner, or look at any existing site analytics.
- Unknown: why people reserve (to hold a scarce cheese, or for an event). Confirm with the owner and customers. This is tied to Q1.
- Exclusion-risk scenario not researched: a screen-reader user making a reservation. Q4 also covers this.

**Competitive analysis: skipped.** No comparison targets or selection criteria were supplied. Gap recorded: there is no view of established patterns for showing daily stock or taking small-business reservations, so stage 3 has no pattern options to draw on.

## Stage 3: Map task flows

**Flow G1: view today's cheeses (R1, R2).** Entry point: opening the app. Success: the visitor sees today's list.

1. Visitor opens the app → the system shows today's cheese list.
2. Decision: is there a list for today?
   - Yes → the list is shown. Success.
   - No (staff haven't updated it, A1) → the system shows a "today's list isn't available yet" state. This is a recoverable exit.
3. Failure: the list doesn't load → the system shows an error with a retry option. Recoverable.

Friction (heuristic, no evidence): a stale list is a risk if A1 fails. No dead ends were found. Every step rests on A1 and A2, so the flow is assumed.

**Flow G2: make a reservation (R3, R4): stopped.** Q1 blocks it. Every step, field, and capacity rule depends on what is being reserved. Mapping it now would mean inventing the core of the flow. The failure-behavior rule applies: a blocking question needs a stakeholder decision, so the workflow stops here and returns a partial result.
