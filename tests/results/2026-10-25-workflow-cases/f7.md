# Fix or Build to Merge: case run

**Case:** Defect cause sits in a design that deserves rework

## Stage 1: Define what the change must do (skipped)

Stage 1 says to skip Refine Issue for a defect when "the report states the expected behavior and the requester confirms it." The fixture says the expected behavior is approved: 3 kg falls in the 1 to 3 kg band, so the upper boundary is inclusive.

The expected behavior carried forward is:
- A 3 kg parcel is charged at the 1 to 3 kg band rate.
- Weights above 3 kg go to the next band.

## Stage 2: Confirm environment (done outside the workflow)

The fixture says the environment is confirmed. The fixture does not give the target branch or the test command, which the stage 2 validation asks for. I take them as confirmed but cannot name them.

## Stage 3: Build or repair (Bug Fix)

1. **Reproduce or reason from evidence.** I reasoned from the evidence; there is no code to run. A boundary check of the form `weight < 3` is false when the weight is exactly 3. The 3 kg parcel then misses the 1 to 3 kg band and falls into the next one. That matches "off by one band."
2. **Smallest cause, separate from the symptom.**
   - Symptom: 3 kg parcels get the wrong shipping cost, one band too high.
   - Cause: the upper boundary of the 1 to 3 kg band is checked with `<` instead of `<=`.
3. **Check that fails because of the defect.** A test asks for the band of a 3.0 kg parcel and expects 1 to 3 kg. Edge companions:
   - 1.0 kg is still in 1 to 3 kg, which confirms the lower bound did not move.
   - 3.01 kg (or the next unit above 3) goes to the next band.
   - **Status:** not run. I have no code, so the "failed before" result was not observed.
4. **Patch without widening scope.** Change that one comparison from `<` to `<=`, and nothing else.
5. **Confirm the pass and run surrounding checks.** Not run, for the same reason. Nothing is reported as passing.
6. **Residual risk:**
   - The rate table is hard-coded across four files. If the same boundary logic is copied into other code paths, those paths may have the same defect. Each copy needs a check for exactly 3 kg (and every other band edge) before this fix counts as complete for the symptom.
   - If another copy is wrong, it is the same cause in a duplicate place. Fixing it would stay in scope only if it is the same one-character boundary change.

**Other defect noticed (mentioned, not fixed):** the duplicated, hard-coded rate table.

## Scope decisions

- **Fix scope:** only the `<=` boundary correction, plus the regression check for the band edges. The diff must touch only what the cause requires, per the stage 3 validation and the Bug Fix check "the diff contains only what the fix needs."
- **Rate table rework:** handed off, not built here. Consolidating a table that is hard-coded across four files is a redesign, larger than the cause justifies. The Branching rule says to "stop and hand it to the requester as a separate work item rather than widening the fix." Bug Fix also says to mention other defects but not fix them.
- **Proposed separate work item, not created:** "Consolidate the shipping rate table into a single source." It would go through its own stage 1 refinement and approval, and is not authorized here.
- **Decisions for the requester:**
  1. Accept the rework as a separate work item, and decide when to do it.
  2. Confirm whether the fix should cover every duplicated boundary that shows the same `<` error, or only the one diagnosed site.

## Stop point

I stopped after stage 3. The workflow needs the failing-before check to be observed failing for the stated reason before regression review (stage 4) can start. That evidence cannot come from the fixture, and the workflow forbids inventing a test result.
