**Problem frame**

**Title:** Travel app happiness
**Prepared:** 2026-10-25. **Requester:** requester, not named in the fixture.

**Goal:** "Our travel app will make people happier." Status: Unconfirmed as a testable question. This is the requester's wording, not a restatement that has been checked with them.

**Validation after stage 1:** fails. There is no result that would refute the question, and the requester explicitly rules one out.

### Return to stage 1 (the one return allowed)

The skill says to propose an observable measure when the stated one cannot be observed. These are candidate reframings for the requester to choose from. They are not adopted, and none is a recommendation:

- (A) *Assumed:* "Users who plan a trip with feature X report less planning stress than users who plan without it, on the same short self-report scale." It confirms if the reported stress is lower by a margin the requester sets ahead of time. It refutes if there is no difference or stress is higher.
- (B) *Assumed:* "At least N of M test users finish task Y and say they would use it again." It confirms if N or more do. It refutes if fewer than N do.

Each of these swaps "happier" for something narrower that can be observed. Only the requester can say whether the narrower claim is the question they care about. The fixture's position is that no result could show the claim wrong. That rules out accepting a refuting result, so on the fixture's terms the question still cannot be refuted after this return.

**Branch taken:** "If the question cannot be made refutable after one return to stage 1, stop and report what would make it testable." Failure behavior also lists "the question cannot be tested" as a reason to stop.

## Stopped: report to requester

The POC is not scoped. A proof of concept settles a question only if some result could go against it, and this claim allows none. To make it testable, the requester needs to:

1. Name the people and situation, for example first-time users planning a trip.
2. Replace "happier" with one observable signal, such as a self-report scale, task completion, or return use.
3. Set before any work starts the result that would confirm the claim and the result that would refute it, and agree to accept a refuting result.

Then the requester can choose to narrow the question as in (A) or (B), give a different one, or drop it. Once a refutable question is confirmed, the three-week, one-person limit is already supplied for stages 3 and 4.
