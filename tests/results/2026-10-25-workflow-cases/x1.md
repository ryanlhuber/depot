# Feature Delivery: "saved searches" (start only)

## Stage 1: Specify, build, review, and merge

Stage 1 is the whole of Fix or Build to Merge, run as written. Feature Delivery does not refine, build, review, or merge anything itself. Stage 1 hands all of that to Fix or Build to Merge, which assigns Feature Build to the builder.

**What Fix or Build to Merge stage 1 (Refine Issue) does now.** The fixture says a work item and conventions exist, but it gives none of their content. So refinement starts from the item's title alone, and I am not inventing requirements. Refine Issue asks about one decision at a time:

> Objective (restated): job-board users can save a search and run it again later. The most important open decision is what "saved" includes.
>
> **[1/5] What does a saved search store and do?**
> A. Query and filters only. The user re-runs it by hand.
> B. A plus a user-chosen name, with rename and delete.
> C. B plus alerts when new jobs match (email or in-app).
>
> Recommendation: B. It delivers the core outcome. Alerts bring in notification delivery, scheduling, and consent, so C is better as a separate work item.

The other planned questions:
- Is there a limit on saved searches per user?
- Do saved searches require sign-in, and what happens to anonymous users?
- What happens when a saved filter value no longer exists?
- Who reads the documentation?

**Recommendation from Feature Delivery stage 3, to include during refinement.** Make the documentation an acceptance criterion in the specification, for example: "Help text for saving, renaming, and deleting a search is updated for job seekers." That way the documentation ships in the reviewed revision, and stage 3 below only has to verify it. Otherwise any documentation edit made after the merge counts as a new change, and it would have to go back through review and merge.

**Risk note for the metadata.** Saved searches store user-linked data, but nothing so far points to authentication changes, credentials, or destructive operations. Proposed risk: medium. This is not high-risk unless refinement adds alerts or sensitive data.

**Where stage 1 stops now:**
- Refinement waits for the requester's answer to [1/5].
- No specification exists yet, so nothing is approved.
- After approval, Fix or Build to Merge still needs things the fixture does not supply:
  - A confirmed environment note (target branch read from project configuration, plus the test command).
  - A builder and two independent reviewers, from three distinct model families if they are models.
- If either of those can't be met, Fix or Build to Merge stops, and Feature Delivery stops with it.
- Fix or Build to Merge skips its own regression review for a feature, because Feature Delivery stage 2 runs it after the merge.

**Validation after stage 1 (not reached yet):** confirm that the merged revision is the revision the reviews examined.

## Later stages I would add, and why

| Stage | Add? | Why |
|---|---|---|
| 2. Regression review | Probably yes, decided after the merge | Saved searches likely reuse the search query and filter contract and add stored user data. Both count as shared contracts or data. If the merged change turns out to be isolated, skip it and record the reason. |
| 3. Documentation | Yes, as verification | Checks the documentation that shipped through the acceptance criterion, including every command and link. If anything is missing, deliver it as a new change. Can run alongside stage 2. |
| 4. Release readiness | Yes | Gives a ready or not-ready verdict for the target environment, with rollout, monitoring, and rollback. Must assess the final merged revision, including any regression fix or documentation change made after stage 1. Does not deploy. |
| 5. Release decision | Yes, made by a human | The requester decides whether and when to release. Never automated. |

None of these stages repeats refinement, build, review, or merge. Any fix they trigger goes back through stage 1 as a new work item.
